## 1. 재설계 원칙 (네 문장)

1. **하루 서사**: 학생은 '한빛 보존연구소'(가상)에 첫 출근한 신입 보존과학자다. 아침에 영상을 보고, 오전~오후에 기록 보관실의 **실제 사건 파일 5개**를 다시 판단하고, 저녁에 **진짜 의뢰(우리 반이 고른 문화유산)**를 받아 해결 프로그램을 만든 뒤 퇴근 보고를 한다.
2. **귀납**: 원칙 이름(P1~P5)은 저녁 '연구 일지 정리' 전까지 학생 화면에 나오지 않는다. 학생은 사건마다 **행동 카드**만 모으고, 마지막에 카드를 직접 묶고 이름 붙여 '우리 반 알고리즘'을 만든다. 그다음에 전문가의 원칙과 비교한다.
3. **개발형**: 우리 반 알고리즘을 **선택 그래프 프로그램**으로 구현한다(설계 → 입력 → 다른 팀이 실행·시험 → 버그 고치기). 학생은 하루 종일 플레이한 게임과 똑같은 모양의 게임을 자기 손으로 만든다.
4. **연결**: 영상 질문 → 사건 근거, 아침에 고른 유산 → 저녁 의뢰, 우리 반 알고리즘 → 프로그램 → AI 점검 기준으로, 앞 단계의 산출물이 반드시 뒤 단계의 입력이 된다.

### 2.2 학습 목표 수정(`docs/01` §4의 '과정·기능' 칸 교체)
> 가상 실습에서 예측하고 관찰한 증거로 선택하고, 다섯 사건의 행동 카드를 묶어 공통 알고리즘을 귀납한다. 그 알고리즘을 **선택 그래프 프로그램으로 설계·구현하고, 다른 팀의 실행 시험으로 오류를 찾아 고친다.** 우리 알고리즘을 기준으로 생성형 AI의 답을 점검한다.

## 3. 하루 서사

### 3.1 무대
- 연구소: **한빛 보존연구소**(가상의 이름, 실제 기관 아님). 상단 바에 이야기 속 시계(예: `오전 10:30`)와 '연구 일지 n장'을 보여 준다.
- 안내자: **연구실장**(이름 없음, 단색 실루엣 아이콘). 단계가 바뀔 때 말풍선 한두 줄. 문구는 `scenario.story.mentor[단계]`.
- 사건 파일: 기록 보관실 상자. 브리핑 첫 줄 위에 "사건 파일 #n · 실제로 있었던 일 · 장소 · 연도" 띠를 붙인다. 시간 여행처럼 꾸미지 않고 **"그때 그 보존과학자의 자리에서 판단해 보기"**로 말한다(사실 왜곡 방지).
- 사건 사이 이음 문구: 연구실장이 앞 사건의 행동 카드 하나를 짚고 다음 파일을 건넨다(예: "아까 우리는 녹의 진짜 까닭을 찾았죠. 이번엔 깨진 유리예요."). 문구는 `scenario.story.bridges[caseId]`.

## 5. 귀납 장치

### 5.1 근거 태그 = 증거 출처
`scenario.reasonTags`를 다음으로 바꾼다(원칙 이름 금지).

```json
[
  {"id": "lab", "label": "실습 결과"},
  {"id": "manual", "label": "매뉴얼"},
  {"id": "video", "label": "아침 영상"},
  {"id": "journal", "label": "앞 사건 일지"}
]
```
근거 배지 규칙(`docs/05` §4)을 바꾼다: 태그가 하나 이상이면 +1, `journal` 태그는 사건 2부터 쓸 수 있다(앞 사건의 경험을 다음 판단에 쓰는 것 자체가 귀납의 씨앗).

### 5.2 행동 카드(연구 일지)
결정 노드마다 `journal` 필드를 추가한다. 문구는 **그 결정에서 ✓였던 행동을 일반적인 행동으로** 쓴다. 실제 역사 공개(S18) 뒤에 보여 주므로 답을 미리 흘리지 않는다. `hiddenPrinciple`은 학생 화면에 나오지 않고 S21 비교와 교사 패널에서만 쓴다.

확정본(기존 `scenario.json`의 ✓ 선택지와 결과 문구에서만 만들었고 새 역사 사실은 없다. 2026-11-03 `kid-reader` 검토 반영):

| 결정 | 행동 카드 | hiddenPrinciple |
|---|---|---|
| c1d1 | 오랜 시간 생긴 초록 녹을 지우지 않고 그대로 남겼어요. | P4 |
| c1d2 | 녹이 생긴 진짜 까닭을 찾았어요. 맞닿은 두 금속을 떼어 놓았어요. | P2 |
| c2d1 | 붙이기 전에 조각마다 번호를 달고 사진으로 남겼어요. | P1 |
| c2d2 | 오래 버티고 나중에 다시 뗄 수 있는지 시험해 보고 접착제를 골랐어요. | P3 |
| c3d1 | 급하게 붙이지 않고 사진과 기록부터 남겼어요. | P1 |
| c3d2 | 가면이 다치지 않게 데운 뒤 나무 도구로 조금씩 뗐어요. | P3 |
| c3d3 | 나중에 다시 뗄 수 있는 밀랍(벌집으로 만든 왁스)으로 붙였어요. | P3 |
| c4d1 | 문제를 숨기지 않았어요. 작업을 멈추고 기록해 알렸어요. | P1 |
| c4d2 | 칠을 조금 떼어 무엇으로 만들었는지 살폈어요. | P2 |
| c5d1 | 나중에 뗄 수 있는 나무 받침으로 잠시 받쳤어요. | P3 |
| c5d2 | 확실히 알 수 있는 층까지만 다시 쌓았어요. | P5 |

예상되는 묶음: 살피고 기록하기 3장 · 진짜 까닭 찾기 2장 · 다시 뗄 수 있게 4장 · 원래 것 남기기 1장 · 증거만큼만 1장. '다시 뗄 수 있게'가 가장 큰 묶음이 되어 접착 허브 질문으로 자연스럽게 이어진다. 학생 묶음이 이와 달라도 그대로 저장하고, S21 비교에서 차이를 토의한다(정답 강요 금지).

### 5.3 반 경로와 일지의 관계
일지 카드는 반이 어떤 선택을 했든 같은 카드다(실제 역사 기준). 반 경로 결과는 카드 테두리에 작은 기호로 함께 남긴다: 반이 ✓를 골랐으면 ✓, 아니면 "실제와 달랐어요 △/✕". 이것이 '우리가 처음엔 몰랐던 행동'을 눈에 띄게 한다.

## 6. 선택 그래프 프로그램 편집기(S31~S33)

### 6.1 데이터 모델
```ts
interface ClassAlgorithmStep { id: string; name: string; cardIds: string[]; order: number }

interface ProgramChoice {
  key: "A" | "B" | "C";
  label: string;                 // 행동 (≤ 45자)
  result: "solved" | "worse" | "irreversible";
  why: string;                   // 결과 까닭 한 줄
  stepId: string | null;         // 근거가 된 우리 반 알고리즘 단계
}
interface ProgramDecision {
  id: string;                    // "p1".."p4"
  owner: TeamId;                 // 설계한 팀
  situation: string;             // 상황/질문
  choices: ProgramChoice[];      // 2~3개
}
interface Program {
  heritage: { name: string; material: string; risk: string };
  decisions: ProgramDecision[];  // 최대 4개, 순서 = 실행 순서
  version: number;               // 고칠 때마다 +1
}
```
상태 추가(`AppState`):
`storyClock`, `morningNotes: string[]`, `heritageTally: Record<string, number>`, `teams[t].heritage`, `journal: {cardId, caseId, classResult}[]`, `clusters: Record<string, string[]>`, `classAlgorithm: ClassAlgorithmStep[]`, `program: Program`, `testRuns: {decisionId, testerTeam, choice, note}[]`, `bugs: {id, decisionId, rule, fixedInVersion?}[]`, `aiTrust: Record<TeamId, {before?: TrustValue; after?: TrustValue}>`.
기존 `algorithmNotes`는 `classAlgorithm`으로 옮기고, 가져오기(JSON 복원)할 때 옛 형식은 그대로 읽어 변환한다.

### 6.2 편집기 화면(프로젝터, 교사 조작)
- 왼쪽: 프로그램 그래프 미리보기(사건 그래프와 같은 SVG 모양, 결정 4개를 왼쪽에서 오른쪽으로).
- 오른쪽: 선택한 결정의 입력 양식(상황 1칸, 선택 A~C 각각 행동·결과 ✓△✕ 버튼·까닭·알고리즘 단계 드롭다운).
- 키보드: `1~4` 결정 선택, `Tab` 칸 이동, `Ctrl+Enter` 저장, `R` 실행 시험으로.
- 글자 수가 45자를 넘으면 칸 테두리에 '길어요' 표시(막지는 않음).
- 입력은 학생 이름 없이 팀 번호만 기록한다.

### 6.3 자동 검사(버그 규칙)
`tools/validate-scenario.mjs`의 그래프 규칙을 재사용해 `src/engine/programCheck.ts`로 만든다. 메시지는 초5 해요체, 원문은 `scenario.programBuilder.bugMessages`.

| 규칙 | 조건 | 학생 메시지(초안) |
|---|---|---|
| B1 빈 칸 | 상황·행동·결과가 비었음 | "아직 비어 있는 칸이 있어요." |
| B2 선택 수 | 선택이 2개보다 적음 | "고를 수 있는 길이 둘 이상 있어야 해요." |
| B3 해결 길 | ✓인 선택이 하나도 없음 | "이 결정에는 해결되는 길이 없어요." |
| B4 근거 | ✓인 선택에 알고리즘 단계가 없음 | "왜 해결됐는지 우리 알고리즘 단계를 골라 주세요." |
| B5 알고리즘 사용 | 우리 반 알고리즘 단계 중 프로그램 어디에도 안 쓰인 단계가 있음(경고) | "'○○' 단계는 아직 프로그램에 없어요. 정말 필요 없을까요?" |
| B6 같은 길 | 두 선택의 행동 문구가 같음 | "두 길이 똑같아요." |

✕ 결과가 있어도 다음 결정으로 진행한다(막다른 길 금지, 기존 규칙과 같음).

### 6.4 실행 시험(S32)
- 시험 팀이 그 결정을 투표한다(기존 투표 UI 재사용, 점수·건강도 없음).
- 결과를 공개한 뒤 교사가 시험 팀의 한 줄 지적을 `testRuns[].note`에 적는다.
- 자동 검사 결과와 지적을 합쳐 S33 버그 목록을 만든다.

### 6.5 종이 대체(W3 설계 카드)
`?mode=print`의 W3를 '팀 설계 카드'로 바꾼다: 의뢰 유산 · 우리 팀 결정(상황) · 선택 A/B/C(행동, 결과 ○△✕ 동그라미, 까닭, 알고리즘 단계 번호). 기존 개인 W3(내 문화유산 보존 계획)는 **W5 집에서 해 보기**로 옮겨 과제로 쓴다.

## 7. AI 조수 점검(S34)

1. 의뢰 유산을 기준으로 한다. 교사가 수업 중 **별도 기기·별도 탭**에서 생성형 AI에 `aiCheck.promptTemplate`(의뢰 유산 이름과 위험을 끼워 넣은 질문)을 묻고 답을 교사 패널에 붙여 넣는다. 앱은 AI에 접속하지 않는다(절대 규칙 4 유지).
2. 붙여 넣은 답이 없으면 기존 사전 캡처 사례(경복궁 담장 낙서, `capturedAnswers`)로 진행한다. 이때도 점검 기준은 아래 3번과 같다.
3. 화면: 왼쪽 AI 답, 오른쪽 **우리 반 알고리즘 단계**(S21에서 만든 이름과 순서)가 점검 항목. 단계마다 '지켰어요 / 빠졌어요 / 모르겠어요'.
4. 그 아래 **우리 프로그램과 나란히 보기**: AI 답의 행동들이 우리 프로그램의 ✓ 길과 같은지 다른지.
5. 믿음 투표: 답을 처음 보여 줄 때 팀별 "믿을 만해요 / 잘 모르겠어요 / 못 믿겠어요" → 점검 후 같은 투표 다시. 변화를 로그에.
6. 기존 고정 체크리스트 5개는 교사 패널 참고용으로 옮긴다.

## 11. Claude Code 작업 순서(Phase R0~R6)

각 Phase는 Plan 모드로 상태 모델과 화면 흐름을 먼저 합의하고, 끝나면 `npm run validate && npm test && npm run build && npm run e2e`가 통과해야 다음으로 간다.

docs/12-redesign.md를 읽고 docs/01~06, src/modes/teacher.ts, src/core/actions.ts, data/scenario.json과 비교해,

docs/12 §9대로 expedition·frame 진입 링크를 없애고 VITE_EXTRAS 빌드 플래그로 분리해.
기본 빌드 크기와 기존 E2E 결과를 보고해. 탐험·프레임 E2E는 EXTRAS 빌드에서만 돌게 해.

검증: 단위 62개, E2E 17개 통과. 하루 전체(세 가지 선택 패턴, 35개 결과 노드 모두), 80분 점심시간 이어하기, 학생 화면 원칙 누출 없음(S21 비교 전), 버그 → 고치기 → 다시 실행 통과, 29개 화면 1920×1080 넘침 없음, 외부 요청 0건. 기본 빌드 약 227 KB.

**문서와 다르게 정한 것**
- 옛 기록(schemaVersion 1) 가져오기는 변환하지 않고 "예전 방식의 기록" 안내와 함께 거부한다. 재설계 전 기록은 Codex 검증 중에만 생겼고 흐름이 달라 이어 할 수 없다.
- `aiCheck.checklist`는 자리를 옮기지 않고 그대로 두되, 교사 도구에만 보인다.
- 80분 프로필의 점심시간은 사건 3 뒤(1차시 끝)다.
- 자막 없는 영상(`-plain.mp4`)이 아직 없어서 1회차에도 자막 판이 재생된다. 자막 다시 합치기(§4.1)는 남은 일이다.
